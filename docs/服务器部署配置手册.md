# MLPro 机器学习平台 · 服务器部署配置手册

> 本手册的服务器基线（操作系统 / 目录约定 / Nginx + systemd 架构 / Python 安装方式）沿用同环境已落地的
> `shenji` 项目《07-信创服务器部署手册》与 `mall` 项目《DEPLOY.md》，仅按 MLPro 自身的技术栈差异做了调整。
>
> - 适用环境：**aarch64（ARM64）+ 统信 UOS Server 20**（x86_64 + CentOS/Ubuntu 同样适用，差异见 §2.2）
> - 网络：**配置阶段临时联网**，装完即可断网，生产运行不依赖外网
> - 部署形态：**Nginx（80 端口）托管前端静态资源 + 反向代理 → uvicorn（FastAPI）**，systemd 守护 + 开机自启
> - 数据库：**SQLite**（随应用本地文件，无需额外数据库服务器）

## 一、部署架构

```
              浏览器（用户电脑）
                   │  http://10.9.14.167:80
                   ▼
 ┌────────────────────────────────────────────────┐
 │        应用服务器 (aarch64 / UOS Server 20)      │
 │                                                │
 │   Nginx (systemd)  监听 0.0.0.0:80             │
 │     ├─ location /       前端静态资源(SPA 回退)   │
 │     │      root /opt/mlpro/frontend/dist       │
 │     └─ location /api/   反向代理 ↓              │
 │              proxy_pass http://127.0.0.1:8000  │
 │                          │                     │
 │   uvicorn (systemd)  监听 127.0.0.1:8000       │
 │     └─ FastAPI (/api/auth /data /workflow      │
 │                 /report)                       │
 │           ├─ SQLite  backend/sql_app.db        │
 │           └─ 用户数据 backend/user_data/{uid}/  │
 │                （uploads / workflows / models） │
 └────────────────────────────────────────────────┘
```

与参考项目的关键差异：

| 关键点     | shenji / mall                         | **MLPro**                                                                                                        |
| ---------- | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 数据存储   | StarRocks `10.9.14.128:9030` + SQLite | **仅 SQLite + 本地文件**，无外部数据库依赖                                                                       |
| 依赖体量   | 纯 Python 包为主，约 30 个 wheel      | **含 numpy / scipy / pandas / scikit-learn / xgboost / lightgbm / matplotlib**，aarch64 wheel 需重点核验（§3.2） |
| 请求耗时   | 查询、导出 Excel                      | **模型训练、报告导出可达数分钟**，Nginx 超时须放大（§5.2）                                                       |
| 上传行为   | 上传单个 xlsx                         | **频繁上传 CSV/Excel 数据集**，`client_max_body_size` 必须调整（§5.2）                                           |
| 运行时资源 | 轻量                                  | 训练占 CPU / 内存，建议 **≥4 核 8G**，磁盘 ≥50G（模型与数据集累积）                                              |

## 二、服务器基线信息

### 2.1 环境约定（与参考项目保持一致）

| 项目           | 取值                                                                                        |
| -------------- | ------------------------------------------------------------------------------------------- |
| 操作系统       | 统信 UOS Server 20（glibc 2.28，满足 python-build-standalone ≥2.17 要求）                   |

| 虚拟环境       | `/opt/mlpro/venv`                                                                           |
| 前端产物       | `/opt/mlpro/frontend/dist`（由 Nginx 托管）                                                 |
| Nginx 站点配置 | `/etc/nginx/conf.d/mlpro.conf`                                                              |
| systemd 服务   | `/etc/systemd/system/mlpro.service`                                                         |
| 对外端口       | 80（8000 仅本机 Nginx 访问，不对外放开）                                                    |
| pip 镜像       | `https://pypi.tuna.tsinghua.edu.cn/simple`                                                  |
| 参考服务器 IP  | **本项目服务器为 `10.9.14.167`**（本手册命令已按此 IP 书写；shenji 应用机为 `10.9.14.144`） |

> ⚠️ 若与 shenji **部署在同一台服务器**，两者都要占用 80 端口，必须二选一：
> ① MLPro 改用其它端口（如 `listen 8080;`，并在防火墙放开 8080）；
> ② 或在同一 `server` 块下用子路径区分（需前端配置 base 路径，改动较大，不推荐）。
> 当前 MLPro 独占 `10.9.14.167`，与 shenji 的 `10.9.14.144` 是两台机器，**不存在端口冲突**，直接用 80 端口即可。

### 2.2 非信创环境的差异

| 环节         | UOS / CentOS / RHEL                             | Ubuntu / Debian                                             |
| ------------ | ----------------------------------------------- | ----------------------------------------------------------- |
| 装 Nginx     | `yum install -y nginx`                          | `apt install -y nginx`                                      |
| 站点配置目录 | `/etc/nginx/conf.d/mlpro.conf`                  | `/etc/nginx/sites-available/mlpro` + 软链到 `sites-enabled` |
| 移除默认站点 | 注释 `/etc/nginx/nginx.conf` 里默认 `server` 块 | `rm -f /etc/nginx/sites-enabled/default`                    |
| 防火墙       | `firewall-cmd --permanent --add-port=80/tcp`    | `ufw allow 80/tcp`                                          |
| Python 3.12  | 预编译包（§4.1）                                | 亦可 `apt install python3.12 python3.12-venv`               |

### 3.1 前端 API 地址改为相对路径（已完成）

`frontend/src/services/api.ts` 原为 `baseURL: 'http://localhost:8000/api'`——用户浏览器上的 `localhost` 指向用户自己的电脑，线上必然请求失败。现已改为同源相对路径：

```ts
// 使用同源相对路径：生产环境由 Nginx 反向代理 /api 到后端，
// 开发环境由 vite.config.ts 的 proxy 转发到 127.0.0.1:8000。
baseURL: '/api',
```

同时 `frontend/vite.config.ts` 已补上开发代理，保证 `npm run dev` 行为与线上一致：

```ts
export default defineConfig({
  plugins: [react()],
  server: {
    proxy: {
      '/api': { target: 'http://127.0.0.1:8000', changeOrigin: true },
    },
  },
})
```

> 该改动使前端**不再依赖任何硬编码后端地址**，换服务器 IP 无需重新构建前端。

### 3.2 后端 CORS（已完成）

### 3.3 报告中文字体（代码已完成，服务器仍需装字体）

原实现依赖 Windows 字体（`['SimHei', ...]`、`TTFont('SimSun', 'simsun.ttc')`），Linux 上会**静默**退化为图表方框 + PDF 中文丢失（有 try/except 兜底，不报错，最易被忽略）。

现已在 `backend/app/api/report.py` 中改为跨平台探测：

- 新增 `_CJK_FONT_CANDIDATES` 候选列表，按 `backend/fonts/` → Windows 系统字体 → Linux 各发行版字体路径依次探测；
- `configure_matplotlib_chinese()` 用 `font_manager.addfont()` 注册探测到的字体文件，再按族名使用，并保留字体名兜底；
- 新增 `register_pdf_chinese_font()`，为 reportlab 注册字体（`.ttc` 自动带 `subfontIndex=0`，OTF/CFF 注册失败会自动尝试下一个候选），结果缓存；全部失败才回落 Helvetica 并打印告警。

**服务器上仍必须提供至少一种中文字体**，二选一：

```bash
# 方式一：安装发行版开源中文字体（无需占用仓库体积，但依赖服务器能装包）
yum install -y wqy-zenhei-fonts        # 或 google-noto-sans-cjk-ttc-fonts
fc-cache -fv

# 方式二：字体随仓库下发（推荐，优先级最高、最可控，不依赖服务器联网装包）
# 开发机操作：把字体放进项目并提交，服务器 git clone/pull 时自动就位
mkdir d:\2-code\mlpro\backend\fonts
copy C:\Windows\Fonts\simhei.ttf d:\2-code\mlpro\backend\fonts\
```

#### 方式二的体积开销（实测值，✅ 已按方式二放入 `backend/fonts/simhei.ttf`）

| 字体文件             | 体积       | 是否必需                                                          |
| -------------------- | ---------- | ----------------------------------------------------------------- |
| `simhei.ttf`（黑体） | **9.3 MB** | ✅ **只需这一个**。它是探测列表的第一顺位，图表与 PDF 正文均使用它 |
| `simsun.ttc`（宋体） | 17.2 MB    | ❌ 可不放。仅当你希望 PDF 正文用宋体时才需要                       |
| 两个都放             | 26.5 MB    | ❌ 不必要                                                          |

**结论：只需提交 `simhei.ttf` 一个文件，9.3 MB。**

Git / GitHub 侧完全不构成问题：

- GitHub 单文件限制：>50 MB 仅告警，>100 MB 才**硬拒绝**。9.3 MB 远低于阈值，**无需 Git LFS**。
- 当前仓库已有对象约 **14.3 MB**，加入字体后约 **24 MB**，仍远小于 GitHub 建议的 1 GB 仓库上限。
- 字体是二进制文件，Git 不做增量存储：**每提交一次新版本就多占 9.3 MB 历史**。字体基本不会变，提交一次即可。
- 对服务器的影响：首次 `git clone` 多下载约 9 MB，临时联网期间可忽略。

> 字体版权提示：将 Windows 字体提交到（尤其是公开的）仓库属授权灰区。内网自用 / 私有仓库一般可接受；
> 若仓库是 **public**，建议改用开源字体提交（如 `wqy-microhei.ttc` 约 4.4 MB、思源黑体/Noto Sans SC 的 **TTF** 版本），
> 文件名只要放到 `backend/fonts/` 下并加入 `report.py` 的候选列表即可。注意 **OTF/CFF 字体 reportlab 不支持**，必须用 TTF/TTC。

验证（部署完成后执行）：

```bash
cd /opt/mlpro/backend
/opt/mlpro/venv/bin/python -c "from app.api import report; print(list(report._iter_cjk_font_files())); print(report.register_pdf_chinese_font())"
# 期望：列出至少一个字体文件路径，且 PDF 字体名输出 MLProCN（输出 Helvetica 说明没找到中文字体）
```

### 3.4 matplotlib 无显示环境（无需改动）

`report.py` 已在导入时执行 `matplotlib.use('Agg')`。systemd 中仍显式设置 `MPLBACKEND=Agg` 与 `MPLCONFIGDIR` 双重保险（§7.1）。

### 3.5 SECRET_KEY 暂不改动（**已知风险，需知悉**）

按当前决定，`backend/app/core/config.py` 的 `SECRET_KEY` 保持硬编码占位串 `"YOUR_SUPER_SECRET_KEY_CHANGE_THIS_IN_PRODUCTION"`，不做环境变量外置。带来的实际风险：

- 该密钥是 JWT 签名密钥，且**已随源码进入 Git 仓库**，任何能看到代码的人都可以自行伪造任意用户的登录令牌；
- 内网、可信使用者范围内影响可控；**若系统后续要对更大范围开放，务必先处理这一项**。

后续想改时只需一行（改完在 systemd 里加 `Environment="MLPRO_SECRET_KEY=<openssl rand -hex 32 的输出>"`）：

```python
SECRET_KEY: str = os.getenv("MLPRO_SECRET_KEY", "dev-only-not-for-production")
```

> 副作用：密钥变更后所有已签发的 token 立即失效，用户需重新登录（一次性影响）。

#### 4.3.1 取消跟踪误入仓库的运行时文件（✅ **已在开发机执行，待提交**）

`.gitignore` 虽然已列出 `backend/user_data/`、`sql_app.db`、`__pycache__/`，但这些文件是在加入忽略规则**之前**就已被跟踪的，`.gitignore` 对已跟踪文件无效。实测当前仍有 **46 个文件**在仓库里：

| 类别     | 文件                                                         | 如不处理的后果                                                   |
| -------- | ------------------------------------------------------------ | ---------------------------------------------------------------- |
| 账号库   | `backend/sql_app.db`                                         | 服务器 `git pull` 会用仓库版本**覆盖线上账号库**，新注册用户消失 |
| 用户数据 | `backend/user_data/1/uploads/*`、`workflows/*.json`（11 个） | 线上用户的工作流与数据集被开发机版本覆盖                         |
| 字节码   | `backend/**/__pycache__/*.pyc`（30 个，含 py38/py312 两套）  | 每次提交都产生噪声 diff；跟服务器本地编译结果冲突                |

更直接的问题：服务器运行后这些文件会被应用改写，`git pull` 会报
`error: Your local changes to the following files would be overwritten by merge`，**直接卡住更新流程**。

处理方式（`--cached` 只从仓库移除，**本地文件不会被删**）——以下命令**已在开发机执行完成**，46 个文件已从索引移除，
但**尚未 commit/push**，需跟 §4.3 的正常提交一并推送（或单独提交）：

```powershell
cd d:\2-code\mlpro
# 下面三条 git rm 已执行过，无需重复（仅作记录 / 供其他环境复现）
git rm -r --cached backend/user_data
git rm --cached backend/sql_app.db
git rm -r --cached backend/app/__pycache__ backend/app/api/__pycache__ backend/app/core/__pycache__ backend/app/db/__pycache__ backend/app/services/__pycache__

# 验证：应无输出（已确认通过）
git ls-files | Select-String -Pattern "__pycache__|sql_app\.db|user_data/"
```

> ❗ 这一步使这些文件从 GitHub 仓库中消失（本地磁盘上仍完整保留，已验证）。
> 若仓库里的示例数据集（如 `train_customers2.csv`）你希望保留为演示数据，建议另建一个不参与运行时的目录
> （如 `samples/`）存放并单独提交，而不要放在 `user_data/` 下。
> 已推送的历史仍含这些文件（体积很小，共 ~2.3 MB，无需改写历史）。

处理完后，以下内容才真正不进仓库：`backend/user_data/`、`sql_app.db`、`*.joblib`、`node_modules`、`dist`、`__pycache__`。

### 5.2 创建虚拟环境并安装依赖

MLPro 依赖中含大量科学计算包，**这是本项目在 aarch64 上最大的风险点**，务必逐项验证。

#### 5.2.1 先做两项预检（装之前，30 秒）

**① glibc 版本——这是全局硬门槛：**

```bash
ldd --version | head -1        # 或 rpm -q glibc
```

为何关键：实测 PyPI 索引，**xgboost 的 aarch64 wheel 只有 `manylinux_2_28` 一种标签**（无 `manylinux2014`），
也就是要求 **glibc ≥ 2.28**。UOS Server 20 正好是 2.28，**刚好卡在下限上**，必须现场确认：

- 输出 ≥ 2.28 → xgboost 可直装
- 输出 < 2.28 → xgboost **任何版本都装不上**（不是换版本能解决的），直接走功能降级（见下表）

**② 让 pip 自己告诉你它能装哪些标签：**

```bash
/opt/mlpro/venv/bin/pip debug --verbose | grep -i aarch64 | head -20
```

列表里出现 `cp312-cp312-manylinux_2_28_aarch64` ⇒ xgboost 能装；
出现 `py3-none-manylinux_2_17_aarch64` / `manylinux2014_aarch64` ⇒ lightgbm 能装。
这比“先装一下看报不报错”快得多（xgboost wheel 有 54 MB）。

#### 5.2.2 安装

```bash

/opt/mlpro/venv/bin/pip install --upgrade pip -i https://pypi.tuna.tsinghua.edu.cn/simple

# 系统级运行库（lightgbm 靠 libgomp，matplotlib 靠 freetype/libpng）
yum install -y libgomp freetype libpng

/opt/mlpro/venv/bin/pip install -i https://pypi.tuna.tsinghua.edu.cn/simple \
  -r /opt/mlpro/backend/requirements.txt

# uvicorn 高性能扩展（requirements.txt 里是素 uvicorn，需单独装）
/opt/mlpro/venv/bin/pip install -i https://pypi.tuna.tsinghua.edu.cn/simple "uvicorn[standard]"

# 关键包导入验证（任何一项报错都不要继续往下走）
/opt/mlpro/venv/bin/python -c "import fastapi, uvicorn, sqlalchemy, pandas, numpy, sklearn; print('base ok')"
/opt/mlpro/venv/bin/python -c "import xgboost, lightgbm; print('boosting ok')"
/opt/mlpro/venv/bin/python -c "import matplotlib, docx, reportlab, joblib; print('report ok')"
/opt/mlpro/venv/bin/python -c "import jose, passlib, bcrypt; print(bcrypt.__version__)"
```

#### 5.2.3 aarch64 wheel 可用性（已对 PyPI 索引实测核对）

| 包                                                                 | aarch64 wheel 状况                                                                              | 处置                                                        |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| numpy / scipy / pandas / scikit-learn                              | ✅ 有 `cp312 manylinux_2_28_aarch64`                                                             | 直装                                                        |
| matplotlib                                                         | ✅ 有 `cp312 manylinux_2_28_aarch64`                                                             | 靠 freetype/libpng，已在 5.2.2 预装                         |
| **xgboost**                                                        | ✅ 有，但**仅 `py3-none-manylinux_2_28_aarch64`**，2.0.1 起各版均提供；wheel 较大（新版 ~54 MB） | **真正的门槛是 glibc ≥ 2.28，不是版本号**；不满足时降级使用 |
| **lightgbm**                                                       | ✅ 有 `py3-none-manylinux2014_aarch64`（glibc ≥ 2.17，门槛宽松），~3 MB                          | 必靠 `libgomp`，缺失时 `yum install -y libgomp`             |
| bcrypt==4.0.1                                                      | ✅ 有 `abi3 manylinux_2_17_aarch64`                                                              | **不要升级**，4.1+ 会触发 passlib 的 `__about__` 告警/报错  |
| cryptography（python-jose 依赖）                                   | ✅ 有 `abi3 manylinux_2_17_aarch64`                                                              | 直装                                                        |
| pydantic-core（pydantic 依赖）                                     | ✅ 有 `cp312 manylinux_2_17_aarch64`                                                             | pydantic 本体是纯 Python，真正编译的是 pydantic-core        |
| uvloop / httptools（uvicorn 扩展）                                 | ✅ 有 `cp312 manylinux_2_17_aarch64`                                                             | 可安心装 `uvicorn[standard]`                                |
| fastapi / SQLAlchemy / joblib / openpyxl / reportlab / python-docx | ✅ 纯 Python（`py3-none-any`）                                                                   | 与平台无关                                                  |

> `requirements.txt` 除 `bcrypt==4.0.1` 外**均未锁版本**，pip 会自动选当前有 wheel 的最新版，
> 在 aarch64 上反而更容易装成功；代价是开发机与服务器版本可能不一致。
> **验证通过后立即固版**：`/opt/mlpro/venv/bin/pip freeze > /opt/mlpro/backend/requirements-server.txt`，
> 并把这个文件收回仓库（参考 shenji 的做法），避免下次部署因上游更新而失败。

**xgboost 装不上时的降级路径**（glibc < 2.28）：从 `requirements.txt` 中注掉 `xgboost`，
并确认 `ml_service.py` 里引用 XGBoost 的算法在前端不可选（或选中时有友好报错）；
源码编译 xgboost 在 aarch64 上耗时长且易失败，**不建议**。

## 六、Nginx 配置

```bash
yum install -y nginx
# 移除/注释默认站点，避免抢占 80 端口
vi /etc/nginx/nginx.conf     # 注释掉默认的 server { listen 80; ... } 块
vi /etc/nginx/conf.d/mlpro.conf
```

写入以下内容：

```nginx
server {
    listen 80;
    server_name _;

    # 解决中文乱码（参考 mall 项目踩坑：未设 charset 会出现页面乱码）
    charset utf-8;
    # 确保 CSS/JS 返回正确 MIME，否则浏览器拒绝应用样式，页面变成无样式骨架
    include /etc/nginx/mime.types;

    # 前端静态资源 + SPA 路由回退
    root /opt/mlpro/frontend/dist;
    index index.html;

    # 数据集上传：默认 1m 远远不够，CSV/Excel 数据集按需放大
    client_max_body_size 200m;

    location / {
        try_files $uri $uri/ /index.html;
    }

    # 带 hash 的构建产物长缓存；index.html 不缓存（避免更新后仍加载旧版本）
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2?)$ {
        expires 7d;
        add_header Cache-Control "public";
    }
    location = /index.html {
        add_header Cache-Control "no-store";
    }

    # 后端接口反向代理
    location /api/ {
        proxy_pass http://127.0.0.1:8000/api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 模型训练 / 报告导出耗时长，前端 axios 超时为 300s，这里留足余量
        proxy_connect_timeout 60s;
        proxy_send_timeout    600s;
        proxy_read_timeout    600s;

        # 大文件上传不做缓冲，降低内存与磁盘占用
        proxy_request_buffering off;
    }
}
```

校验：

```bash
nginx -t          # 输出 syntax is ok / test is successful
```

### 7.1 后端服务

```bash
vi /etc/systemd/system/mlpro.service
```

```ini
[Unit]
Description=MLPro Machine Learning Platform (FastAPI + Uvicorn)
After=network.target

[Service]
Type=simple
User=root
# 必须为 backend 目录：SQLite 用相对路径 ./sql_app.db
WorkingDirectory=/opt/mlpro/backend
Environment="PATH=/opt/mlpro/venv/bin"
Environment="LANG=zh_CN.UTF-8"
```

## 九、数据持久化与备份

服务器上**不在 Git 仓库中、必须单独备份**的内容：

| 路径                            | 内容                                                     | 备份建议                         |
| ------------------------------- | -------------------------------------------------------- | -------------------------------- |
| `/opt/mlpro/backend/sql_app.db` | 用户账号表                                               | 每日                             |
| `/opt/mlpro/backend/user_data/` | 各用户的上传数据、工作流 JSON、`*.joblib` 模型、预测结果 | 每日；数据量随使用增长，注意磁盘 |

```bash

#!/bin/bash
# MLPro 数据备份：打包 SQLite 与用户数据目录，保留最近 7 天

    -C /opt/mlpro/backend sql_app.db user_data
find "$DEST" -name 'mlpro_data_*.tar.gz' -mtime +7 -delete
EOF
chmod +x /opt/mlpro-backup.sh
# 每天 02:00 执行
echo "0 2 * * * /opt/mlpro-backup.sh" >> /var/spool/cron/root
```

## 十、更新升级流程

同步方式已固定为：**后端走 GitHub `git pull`，前端在开发机 `npm run build` 后上传 `dist/`**。

### 10.1 后端代码更新（GitHub）

```bash
cd /opt/mlpro
git pull origin main
# requirements.txt 有变动时
/opt/mlpro/venv/bin/pip install -i https://pypi.tuna.tsinghua.edu.cn/simple -r backend/requirements.txt
systemctl restart mlpro
```

> 前提：已完成 §4.3.1 的取消跟踪。否则 `user_data/`、`sql_app.db` 仍在仓库中被跟踪，
> `git pull` 会覆盖生产数据，或因本地修改相冲而直接报错中断。
> 完成后，`user_data/`、`sql_app.db`、`venv/` 不参与版本控制，`git pull` 不会碰它们。

### 10.2 仅前端更新

```powershell
# 开发机
cd d:\2-code\mlpro\frontend; npm run build
scp -r d:\2-code\mlpro\frontend\dist root@10.9.14.167:/opt/mlpro-frontend-dist
```

```bash
# 服务器
rm -rf /opt/mlpro/frontend/dist
mv /opt/mlpro-frontend-dist /opt/mlpro/frontend/dist
systemctl reload nginx
```

> `dist/` 已在 `.gitignore` 中，不进仓库，因此前端更新与 `git pull` 完全解耦：
> 只改前端时不需要 `git pull`，也不需要重启后端服务。

### 10.3 服务器无法访问 GitHub 时的离线更新

信创内网常见场景。在开发机用 `git archive` 导出当前提交的纯净代码（自动排除未跟踪文件）：

```powershell
cd d:\2-code\mlpro

scp d:\mlpro-src.tar.gz root@10.9.14.167:/opt/
```

```bash
# 服务器：只覆盖代码，不碰 user_data/、sql_app.db、venv/
cd /opt/mlpro
tar -xzf /opt/mlpro-src.tar.gz -C /opt/mlpro
systemctl restart mlpro
```

> `git archive` 只包含被跟踪的文件，所以 §4.3.1 完成后它不会携带运行时数据；
> 而 `backend/fonts/simhei.ttf` 已被跟踪，会随包一起下发。

## 十一、常见问题排查

| 现象                                                                   | 原因 / 处理                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 页面能打开，所有接口失败、控制台报 `localhost:8000` 连接被拒           | §3.1 未改 `baseURL`，或构建产物是旧的。重新 `npm run build` 并检查产物中无 `localhost:8000`                                                                                                                                                                                                                                                                                                 |
| 上传数据集报 **413 Request Entity Too Large**                          | Nginx `client_max_body_size` 太小，调大后 `systemctl reload nginx`                                                                                                                                                                                                                                                                                                                          |
| 训练/导出报告到一半 **504 Gateway Time-out**                           | Nginx `proxy_read_timeout` 不足；同时注意前端 axios 超时为 300s，超过需一并调整                                                                                                                                                                                                                                                                                                             |
| 接口 **502 Bad Gateway**                                               | 后端没起来。`systemctl status mlpro`、`journalctl -u mlpro -n 100`、`curl http://127.0.0.1:8000/` 排查                                                                                                                                                                                                                                                                                      |
| 刷新页面 404                                                           | 缺 SPA 回退。确认 `try_files $uri $uri/ /index.html;` 且 `dist/index.html` 存在                                                                                                                                                                                                                                                                                                             |
| 页面乱码 / 样式全丢                                                    | Nginx 缺 `charset utf-8;` 或未 `include mime.types;`（mall 项目实测根因）。改完 `nginx -t` + `reload` + 浏览器 Ctrl+F5                                                                                                                                                                                                                                                                      |
| PDF/图表中文变方框或乱码                                               | 服务器缺中文字体，见 §3.3。先跑 §3.3 的验证命令：字体列表为空或 PDF 字体输出 Helvetica 即未装字体；`fc-list \| grep -i -E "simhei\|simsun\|wqy\|noto"` 辅助确认                                                                                                                                                                                                                             |
| 报告导出报 `Could not find a font` / 图片空白                          | `MPLBACKEND=Agg` 未生效，或 `MPLCONFIGDIR` 不可写导致 matplotlib 初始化失败                                                                                                                                                                                                                                                                                                                 |
| `pip install` 报 `No matching distribution found for xgboost/lightgbm` | 该版本无 aarch64 wheel。降/换版本，或见附录 B                                                                                                                                                                                                                                                                                                                                               |
| 导入 lightgbm 报 `libgomp.so.1: cannot open`                           | `yum install -y libgomp`                                                                                                                                                                                                                                                                                                                                                                    |
| 训练时整机卡顿、其它接口无响应                                         | 未限制 BLAS 线程。确认 systemd 的 `OMP_NUM_THREADS`，必要时下调                                                                                                                                                                                                                                                                                                                             |
| `database is locked`                                                   | SQLite 并发写冲突。`--workers` 降为 1                                                                                                                                                                                                                                                                                                                                                       |
| 登录后频繁 401 掉线                                                    | 本项目 `SECRET_KEY` 为硬编码常量（§3.5），重启不会变化，正常不应出现此现象；若出现请查 token 是否过期（默认有效期 1 天）或浏览器 `localStorage` 被清空                                                                                                                                                                                                                                      |
| 政企定制浏览器（奇安信/360，Chromium 69~86）样式大面积丢失             | Ant Design 的 CSS-in-JS 默认用 `:where(.css-hash)`（需 Chrome 88+），低内核整条规则跳过。参考 shenji《08-奇安信浏览器兼容修复方案》：用 `StyleProvider hashPriority="high"` + `legacyLogicalPropertiesTransformer` 包裹应用根节点，并把构建 target 降低。**注意 MLPro 用的是 antd 6，对现代浏览器特性依赖更深，该方案能否完全解决须实测**；若目标客户端确定为低内核浏览器，建议提前专项验证 |

## 附录 B：离线 wheel 安装（无法在线 pip 时备选）

在联网的 Windows 开发机执行（PowerShell 用反引号换行）：

```powershell
cd d:\2-code\mlpro\backend

D:\3-anaconda\envs\py312\python.exe -m pip download -r requirements.txt `
  --platform manylinux_2_17_aarch64 `
  --platform manylinux2014_aarch64 `
  --platform manylinux_2_28_aarch64 `
  --python-version 312 `
  --implementation cp `
  --abi cp312 `
  --only-binary=:all: `
  -d wheels-aarch64
```

> 上面的 `--implementation cp --abi cp312` 不会误杀 `py3-none-<平台>` 和 `abi3` 类 wheel——已用 pip 自身的
> `TargetPython` 标签集核对：在上述参数下 pip 共接受 96 个标签，其中同时含有
> `py3-none-manylinux_2_28_aarch64`（xgboost）、`py3-none-manylinux2014_aarch64`（lightgbm）、
> `cp312-cp312-manylinux_2_28_aarch64`（numpy 等）、`cp38-abi3-manylinux_2_17_aarch64`（bcrypt）与 `py3-none-any`。

把 `wheels-aarch64/` 传到服务器 `/opt/wheels-aarch64/`，离线安装：

```bash
/opt/mlpro/venv/bin/pip install --no-index \
  --find-links=/opt/wheels-aarch64 \
  -r /opt/mlpro/backend/requirements.txt
```

> MLPro 的科学计算依赖体积较大（numpy/scipy/sklearn/xgboost/lightgbm/matplotlib 合计约 300–500MB），
> 下载与传输耗时明显长于 shenji 项目，请预留时间。
> 某个包缺 aarch64 wheel 时：优先降版本找有 wheel 的版本；其次 `pip download <pkg> --no-binary=:all:` 拿源码在服务器编译
> （需 gcc/make 及对应开发库，scipy/xgboost 源码编译耗时长且易失败，**不建议**）；
> 最后考虑功能降级（例如暂不启用 xgboost/lightgbm 算法）。
